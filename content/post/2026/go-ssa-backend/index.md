## 概要

『基礎から学ぶTinyGo組み込み開発』を読んでいたところ、ビルドプロセスの説明で「SSA」という言葉が出てきました。
なんとなく「最適化に使うやつ」くらいの認識で読み飛ばしていたのですが、そもそもSSAが何なのかを自分の言葉で説明できないことに気づいたので、腰を据えて調べてみました。

この記事では、ビルドプロセスの細かい流れそのものには深入りせず、**「SSAって結局なんなの？」という疑問に答えること**を目的にしています。
調べる中で自分が実際に抱いた疑問を、順番に並べていく形でまとめました。

## そもそもSSAとは何か

**SSA（Static Single Assignment / 静的単一代入）** は、コンパイラが内部で使う**中間表現**の一形式です。

コンパイラはソースコードからいきなり機械語を作るわけではなく、間に「扱いやすい中間の形」を何段階か挟みます。
この中間の形のことを **IR（Intermediate Representation / 中間表現）** と呼びます。

```
Goソース → …… → IR（いくつかの形） → 機械語
```

SSAはこのIRの一種で、**たった一つのルール**を課したものです。

> すべての変数は、プログラム中でちょうど一度だけ代入される。

たとえば、普通のコードはこう書けます。

```go
x := 1
x = x + 2
y := x * 3
```

`x` に2回代入していますね。これをSSAに変換すると、代入のたびに**新しい名前（バージョン）**を振ります。

```
x1 = 1
x2 = x1 + 2
y1 = x2 * 3
```

`x1`、`x2` と番号を振って「一度きりの代入」にする。SSAがやっていることは、まずはこれだけです。

## 疑問1：なぜわざわざ名前を振り直すのか

正直、最初に見たときは「なんでこんな面倒なことをするんだろう？」と思いました。
`x` のままでいいじゃないか、と感じたわけです。

調べてわかったのは、単一代入にすると**「その値がどこで作られたのか」が名前だけで一意に決まる**ということでした。

普通のコードだと、`x` を見ても「今の `x` はどの代入の結果なのか？」をコードを遡って追いかける必要があります。
分岐やループがあると、この追跡が一気に面倒になります。

一方でSSAでは、`x2` と書いてあれば、その定義は**世界にただ一つ**（`x2 = x1 + 2`）しかありません。
なのでコンパイラは、

- この値は定数か？
- この値はもうどこからも使われていないか？

といったことを、**名前を照合するだけ**で判断できます。
この「どの値が、どこで定義され、どこで使われるか」の対応を **use-def関係** と呼ぶそうです。SSAはこれが自明になる形式、というわけですね。

## 疑問2：それで結局何が嬉しいのか

use-def関係が自明になると、コンパイラの**最適化**がとても書きやすくなります。

たとえば、こんな最適化があります。

- **定数伝播・定数畳み込み** … `x1 = 1` という定数の情報を後続に伝播させ（定数伝播）、`x2 = 1 + 2` を `x2 = 3` に計算してしまう（定数畳み込み）
- **デッドコード除去** … どこからも使われていない `xN` は、丸ごと消してしまう

つまりSSAは、**単一代入そのものが速いのではなく、後段の最適化をやりやすくするための土台**だったのです。
ここが腑に落ちると、「ビルドプロセスでSSAが出てくる」理由もなんとなく見えてきました。
機械語にする前に、こうした最適化をしやすい形へ一度変換しているというわけですね。

## おわりに

今回わかったことを、ざっくりまとめておきます。

- **SSA** はコンパイラが使う中間表現（IR）の一形式で、「変数への代入は一度きり」というルールを課したもの
- 代入のたびに `x1`、`x2` と名前を振り直すことで、**値の出所（use-def関係）が名前だけで一意に決まる**
- その結果、定数畳み込みやデッドコード除去といった**最適化が書きやすくなる**。SSAは最適化の土台

「ビルドプロセスでSSAが出てくる」とだけ聞くと身構えてしまいますが、
要は「機械語にする前に、最適化しやすい形へ一度変換している」というだけの話でした。

分岐があるとどうなるのか（φ関数）や、`GOSSAFUNC` で実際の変換を覗いてみる話は、また気が向いたら追記したいと思います。
