## はじめに

『基礎から学ぶTinyGo組み込み開発』を読んでいたら、ビルドプロセスの説明で「SSA」という言葉が出てきた。
なんとなく「最適化に使うやつ」くらいの認識で読み飛ばしていたけれど、そもそもSSAが何なのかを説明できないことに気づいたので調べてみた。

ビルドプロセスの細かい流れそのものには今回あまり踏み込まず、**「SSAって結局なんなの？」という疑問に答える**ことを目的にする。
調べる中で自分が実際に抱いた疑問を、順番に並べていく形で書いた。

## そもそもSSAとは何か

**SSA = Static Single Assignment（静的単一代入）** は、コンパイラが内部で使う**中間表現**の一形式。

コンパイラはソースコードからいきなり機械語を作るわけではなく、間に「扱いやすい中間の形」を何段階か挟む。
この中間の形のことを **IR（Intermediate Representation / 中間表現）** と呼ぶ。

```
Goソース → …… → IR（いくつかの形） → 機械語
```

SSAはこのIRの一種で、**たった一つのルール**を課したものだ。

> すべての変数は、プログラム中でちょうど一度だけ代入される。

普通のコードはこう書ける。

```go
x = 1
x = x + 2
y = x * 3
```

`x` に2回代入している。これをSSAに変換すると、代入のたびに**新しい名前（バージョン）**を振る。

```
x1 = 1
x2 = x1 + 2
y1 = x2 * 3
```

`x1`, `x2` と番号を振って「一度きりの代入」にする。SSAがやっていることは、まずはこれだけ。

## 疑問1：なぜわざわざ名前を振り直すのか

正直、最初に見たときの感想は「なんでこんな面倒なことを？」だった。
`x` のままでいいじゃないか、と。

調べてわかったのは、単一代入にすると**「その値がどこで作られたか」が名前だけで一意に決まる**ということ。

普通のコードだと、`x` を見ても「今の `x` はどの代入の結果なのか？」をコードを遡って追いかけないといけない。
分岐やループがあると、この追跡が一気に面倒になる。

SSAでは `x2` と書いてあれば、その定義は**世界にただ一つ**（`x2 = x1 + 2`）しかない。
だからコンパイラは「この値は定数か？」「この値はもうどこからも使われていないか？」を、**名前を照合するだけ**で判断できる。

この「どの値が、どこで定義され、どこで使われるか」の対応を **use-def関係** と呼ぶらしい。SSAはこれが自明になる形式、というわけだ。

## 疑問2：それで結局何が嬉しいのか

use-def関係が自明になると、コンパイラの**最適化**が書きやすくなる。

- **定数畳み込み** … `x1 = 1` が定数だと分かれば、`x2 = 1 + 2` を `x2 = 3` に畳める
- **デッドコード除去** … どこからも使われていない `xN` は、丸ごと消せる

つまりSSAは、**単一代入そのものが速いのではなく、後段の最適化をやりやすくするための土台**だった。
ここが腑に落ちると、「ビルドプロセスでSSAが出てくる」理由もなんとなく見えてくる。
機械語にする前に、こういう最適化しやすい形へ一度変換しているわけだ。

## おわりに

今回わかったのは、ざっくり次のことだった。

- **SSA** はコンパイラが使う中間表現（IR）の一形式で、「変数への代入は一度きり」というルールを課したもの
- 代入のたびに `x1`, `x2` と名前を振り直すことで、**値の出所（use-def関係）が名前だけで一意に決まる**
- その結果、定数畳み込みやデッドコード除去といった**最適化が書きやすくなる**。SSAは最適化の土台

「ビルドプロセスでSSAが出てくる」とだけ聞くと身構えてしまうけれど、
要は「機械語にする前に、最適化しやすい形へ一度変換している」というだけの話だった。

分岐があるとどうなるか（φ関数）や、`GOSSAFUNC` で実際の変換を覗いてみる話は、また気が向いたら追記したい。
